# 03. Instructions, Knowledge, Tools, and Models in the New Copilot Studio Experience

In the new Microsoft Copilot Studio experience, the Build tab brings the most important agent configuration elements into one place. Instead of starting with explicit topic flows and branching logic, makers now define what the agent should do, what it should know, which systems it can interact with, and which AI model should power its reasoning. Microsoft describes the Build tab as the place to define agent behavior, connect knowledge, add tools, set constraints through instructions, select the AI model, and configure Microsoft IQ sources.

The four most important building blocks are:
<pre>
Instructions → Knowledge → Tools → Models
</pre>

These components decide how useful, safe, accurate, and enterprise-ready your Copilot Studio agent becomes.

## Why These 4 Components Matter
A Copilot Studio agent is not just a chatbot. It is a reasoning-based agent that can understand user intent, retrieve information, use enterprise context, call actions, and respond in a structured way.

Each component has a different role:

| Component | Purpose |
|-----------|---------|
| Instructions | Define the agent's behavior and constraints |
| Knowledge | Provide the agent with relevant information |
| Tools | Enable the agent to interact with external systems |
| Models | Power the agent's reasoning and decision-making capabilities |

In the new experience, agent behavior is mainly driven by instructions and enhanced orchestration rather than explicit topic triggers. Microsoft notes that the new experience uses instructions as the primary mechanism for controlling agent behavior, and the enhanced orchestration runtime interprets these instructions when responding to users.

## 01. Instructions: The Agent’s Behavior Policy
Instructions are one of the most important parts of the new Copilot Studio experience.

In simple terms, instructions tell the agent:
<pre>	
Who you are
What you should do
What you should not do
How you should respond
When you should ask for clarification
When you should escalate
Which tools or knowledge sources you should use
</pre>

**[Microsoft's Documentation](https://learn.microsoft.com/en-us/microsoft-copilot-studio/agents-experience/authoring-instructions) explains that instructions shape the agent’s behavior, tone, and scope. Instructions tell the agent what to do, how to respond, and what to avoid.

### What Good Instructions Should Include?
A strong instruction set should cover these areas:

| Instruction Area | What to define |
|------------------|----------------|
| Role | What the agent is responsible for |
| Scope | What topics the agent can answer |
| Tone | How the agent should communicate |
| Boundaries | What the agent must avoid |
| Knowledge usage | Which sources should be used |
| Tool usage | When tools should be called |
| Clarification | When the agent should ask follow-up questions |
| Escalation | When the agent should hand off or redirect |

Example: If you are building an agent for a HR Policy assistant scenario, your instructions might include:
<pre>
You are an internal HR policy assistant.

Your role is to help employees understand approved HR policies, leave rules, onboarding guidance, and benefits information.

Use only connected HR policy knowledge sources when answering policy-related questions.

Respond in a professional, concise, and supportive tone.

Do not provide legal, medical, payroll, or employment decision advice.

If the user asks for an exception, approval, or personal HR decision, guide them to contact the HR operations team.

If the user’s question is unclear, ask one clarification question before answering.
</pre>

### Why Instructions Must Match Configured Capabilities?
A common mistake is writing instructions for something the agent cannot actually do.
For example, writing this instruction is not enough:
<pre>Search the HR FAQ website before answering.</pre>

The HR FAQ website must also be added as a knowledge source.

An agent cannot act on instructions to use tools, knowledge sources, other agents, or topics that it does not have. The agent must first be configured with the appropriate tools, agents, and knowledge sources.

So the rule is:
<pre>Instructions must be grounded in configured knowledge, tools, agents, topics, variables, or Power Fx expressions.</pre>

### Instruction Writing Best Practices
Use clear, direct, action-oriented instructions.

| Weak Instruction | Strong Instruction |
|------------------|------------------|
| Help users with HR | Answer only HR policy, leave, onboarding, and benefits questions using approved HR sources|
| Be professional | Use a concise, professional, and supportive tone |
| Use the ticket tool | Use the HR ticket creation tool only when the user explicitly asks to create a support request |
| Don’t answer risky questions | Do not provide legal, medical, payroll, or employment decision advice |
| Ask if needed | Ask one clarification question when the user request is ambiguous |

**[Configure high-quality instructions](https://learn.microsoft.com/en-us/microsoft-copilot-studio/guidance/generative-mode-guidance)** to ensure the agent behaves as intended. Poorly written instructions can lead to unexpected or unsafe behavior.

## 02. Knowledge: The Agent’s Information Foundation
Knowledge defines the information sources the agent can use to answer questions. In Copilot Studio, knowledge sources help agents use enterprise data from Power Platform, Dynamics 365, websites, and external systems. Microsoft states that knowledge sources allow agents to provide relevant information and insights by grounding responses in configured sources.

Knowledge can include:

| Knowledge Source | Example Use |
|------------------|-------------|
| SharePoint | Company policies, HR documents, internal wikis |
| Uploaded documents | PDF, Word, or Excel files containing reference material |
| Public Websites | FAQs, product documentation, or support pages |
| Dataverse | Customer data, product information, or internal records |
| Dyanamics 365 | CRM data, sales records, or service information |
| Enterprise connectors | Access to third-party systems like Salesforce, ServiceNow, or SAP |
| Microsoft IQ | AI-powered search and insights from enterprise data |

### Knowledge Design Principle
Do not add knowledge randomly.

The better question is:
<pre>Which source is authoritative for this answer?</pre>

For enterprise agents, knowledge should be:

| Quality | Meaning |
|---------|---------|
| Authorative | Comes from an approved business source |
| Current | Maintained and updated regularly |
| Accessible | Available to the right users only |
| Scoped | Relevant to the agent’s purpose |
| Governed | Aligned with security and compliance expectations |
| Testable | Can be validated during preview and evaluation |

This prevents the agent from becoming a generic answer engine. It stays focused on approved business information.

### Important Knowledge Consideration: User Access
For enterprise scenarios, access control is critical.

For SharePoint, Dataverse, and enterprise data with Microsoft Copilot connectors, authentication is required. The agent user authentication means the agent only surfaces content that the specific user can access. That means the agent should not bypass enterprise permissions. If a user cannot access a SharePoint file directly, the agent should not expose that content through the conversation.

## 03. Tools: The Agent’s Ability to Take Action
Knowledge helps the agent answer. **Tools** help the agent act. Tool is building blocks that let an agent interact with external systems. Tools allow agents to perform actions such as sending emails, checking weather, reading and writing Dataverse data, or posting messages to Teams

In the new Copilot Studio experience, tools and skills are configured from the Build tab. Supported tool types include Power Platform connectors, MCP servers, REST APIs, and agent flows.

### Common Tools

| User Request | Tool Needed |
|--------------|-------------|
| Create a support ticket | Ticketing system connector - ServiceNow, Dataverse or REST API |
| Send this summary to my manager | Email connector - Outlook or Microsoft Graph API |
| Post this update to the team | Teams connector - Microsoft Graph API |
| Check the weather | Weather API connector - REST API |
| Check customer order status | Dataverse or Dynamics 365 connector - REST API |

### How the Agent Decides Which Tool to Use?
In the new experience, makers do not define explicit triggers for tools in the same way as classic topic triggers. The enhanced orchestration runtime decides when to invoke a tool or skill based on the user’s message, conversation context, agent instructions, and the description and configuration of each tool or skill. This makes tool naming and description very important.

### Tool Description Best Practice
Bad tool description:
<pre>Creates record.</pre>

Better tool description:
<pre>
Use this tool when the user wants to create a new HR support request. 
Collect the issue category, employee email, summary, and priority before submitting.
Do not use this tool for policy explanation questions.
</pre>

Good tool descriptions help the orchestrator understand when the tool should and should not be used.

A well-designed agent usually needs both: **Knowledge** to answer questions and **Tools** to take action. For example, an HR agent may need knowledge about leave policies and a tool to submit leave requests.

<pre>
User: I want to understand maternity leave policy.

Agent: Uses knowledge source.

User: I want to raise a maternity leave query with HR.

Agent: Uses HR ticket creation tool.
</pre>

## 04. Models: The Agent’s Reasoning Engine
The selected model affects how the agent reasons, responds, and performs. The model used by the agent affects reasoning capabilities, response quality, and performance. More capable models can handle complex multi-step reasoning, while some models may respond faster but be less capable for complex tasks.

In the new experience, model selection is available from the Build tab components panel.

### Model Selection Considerations
When selecting a model, consider the following:

| Requirement | Model Consideration |
|-------------|-------------------|
| Simple FAQ | Use a smaller, faster model for quick responses |
| Complex reasoning | Use a larger, more capable model for multi-step reasoning and nuanced understanding |
| Enterprise Policy interpretation | Use a model that can understand and apply enterprise-specific instructions and knowledge sources |
| Sensitive Data | Use a model that supports enterprise security and compliance requirements |

### Admin Control for Model Selection
Model selection is also a governance topic.	Administrators can allow or block preview and experimental models in an environment.

Also notes that data processed by preview or experimental models might be processed and stored outside the organization’s geographical boundaries, and cross-region data movement may need to be enabled.

This is important for enterprise architecture because model choice can affect:
<pre>
Data residency
Compliance
Cost
Performance
Risk
Production readiness
</pre>

## Example: Complete Agent Design
### Agent Name
`HR Policy Assistant`

### Instructions
<pre>
You are an HR policy assistant for employees.

Answer questions only about HR policies, leave, benefits, onboarding, and employee guidance.

Use connected HR policy knowledge sources before responding.

If the answer is not available in the approved knowledge sources, say that you do not have enough information and suggest contacting HR.

Do not provide legal, medical, payroll, or personal employment decision advice.

If the user asks for an exception, approval, or case-specific HR decision, guide them to raise a support request.

Use a professional, concise, and supportive tone.
</pre>

### Knowledge Sources
<pre>
SharePoint HR policy library
Employee handbook
Benefits guide
Onboarding guide
</pre>

### Tools
<pre>
Create HR support request
Send HR confirmation email
Retrieve employee support request status
</pre>

### Model
<pre>Production-approved model selected based on reasoning need, latency, cost, and governance policy.</pre>

## Closing Thoughts
The new Copilot Studio experience makes agent creation easier, but it also makes design discipline more important. A good agent is not just built by adding a prompt or connecting a document.

A good agent is designed by carefully aligning:
<pre>
Clear instructions
Trusted knowledge
Controlled tools
Approved model selection
</pre>

That is what turns a simple chatbot into a reliable enterprise AI agent.
