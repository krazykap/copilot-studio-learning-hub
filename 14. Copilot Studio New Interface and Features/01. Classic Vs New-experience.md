# 01. Classic vs New Experience in Microsoft Copilot Studio
Microsoft Copilot Studio is going through an important shift. Earlier, most makers designed copilots using a classic chatbot-style experience, where the focus was on topics, triggers, conversation nodes, branching logic, actions, and explicit flows.

With the new Copilot Studio experience, Microsoft is moving toward an agent-first authoring model. Instead of starting with topics and nodes, makers now start by describing the agent’s purpose, instructions, knowledge, tools, skills, model, and behavior in a more natural-language-driven way. Microsoft describes the new experience as a redesigned authoring and runtime environment for building AI agents, with natural-language-first creation, a unified authoring surface, and enhanced orchestration for better reasoning and response quality.

This change is not only a UI refresh. It changes how we think about designing, testing, governing, and scaling AI agents.

## Why this comparison matters
Many Copilot Studio makers are familiar with the classic interface. They know how to create topics, configure trigger phrases, add message nodes, ask questions, call Power Automate flows, use conditions, and publish the agent.

The new experience introduces a different mental model.

Instead of asking:
<pre>
“Which topic should trigger this conversation?”
</pre>

we now start asking:
<pre>
“What should this agent know, what should it be allowed to do, and how should it reason?”
</pre>

That is the core difference. The classic experience is more **conversation-flow driven** and the new experience is more **agent-behavior driven**.

## Classic Experience: Topic and Flow-Based Design
The classic experience is built around explicit conversation design. In this model, the maker usually creates:

| Area | What it means |
|------|----------------|
| Topics | Conversation path for specific inser intents |
| Trigger Phrases | Phrases that start a conversation on a topic |
| Nodes | Individual messages or actions in a conversation |
| Branching Logic | Conditional paths based on user input or context |
| Actions | Calls to external services, APIs, or Power Automate flows |
| Settings | Configuration options for the agent, such as authentication, channels, generative AI, publishing options, language, voice, and many more |

The classic experience was being organized around topics, flows, branching logic, and explicit configuration nodes. The canvas remains the primary authoring surface, and the left navigation separates areas such as Topics, Knowledge, Actions, and Settings.

This model works well when you need strong control over each step in the conversation.

For example, an IT helpdesk bot may need to ask:
- What issue are you facing?
- Which device are you using?
- Is this urgent?
- Should a ticket be created?
- Which assignment group should receive it?

In such cases, classic topic-based design gives the maker detailed control.

## New Experience: Agent-First Design
The new experience starts with the agent itself. Instead of designing every conversation path manually, the maker defines:

| Area | What it controls |
|------|------------------|
| Purpose | The agent's main function or goal |
| Instructions | Agent role, tone, boundaries, behavior, and escalation rules |
| Knowledge | Information the agent should know - files, SharePoint, Microsoft 365 data, Dataverse, web, or other sources |
| Tools | Capabilities or integrations the agent can use - actions the agent can perform |
| Skills | Abilities the agent has for performing tasks - reusable structured capabilities |
| Model | The AI model the agent uses for reasoning and response generation |
| Behavior | How the agent interacts with users and makes decisions |
| Connected Agents | Other agents that this agent can call or collaborate with to handle specialist tasks |

With the new experience, authoring starts with a natural-language description of the agent’s purpose and behavior. A single tab-based surface consolidates identity, knowledge, tools, skills, and settings. Instructions and reasoning drive the agent’s behavior instead of explicit topic flows.

This makes the new experience more aligned with modern AI agent design.

For example, instead of creating many separate topics for an HR assistant, you can define the agent as:
<pre>
“You are an HR policy assistant. Answer employee questions using approved HR policy documents. Keep responses concise, professional, and grounded in the available knowledge. If the user asks for a policy exception or personal HR decision, guide them to contact HR.”
</pre>

This instruction-based approach becomes the foundation of the agent.

## Navigation Difference
One of the easiest ways to identify which experience you are using is the navigation.

| Classic Experience | New Experience |
|--------------------|----------------|
| Topics, Knowledge, Actions, Settings | Purpose, Instructions, Knowledge, Tools, Skills, Model, Behavior, Connected Agents |
| Left navigation with separate areas | Single tab-based surface with consolidated areas |
| Explicit conversation flow design | Natural-language-driven agent behavior design |

In the classic experience, the maker sees separate areas such as Topics, Knowledge, Actions, and Settings. In the new experience, the agent surface is organized around Build, Preview, Evaluate, and Monitor tabs.

This is an important improvement because the new interface reflects the full lifecycle of an agent:
- **Build:** Define the agent’s purpose, instructions, knowledge, tools, skills, model, and behavior.
- **Preview:** Test the agent’s behavior in a simulated environment.
- **Evaluate:** Assess the agent’s performance, reasoning, and response quality.
- **Monitor:** Track the agent’s usage, performance, and any issues in real-time.

The new interface encourages makers to think beyond just building the agent. It also brings testing, evaluation, and monitoring closer to the authoring experience.

## Side-by-Side Comparison

| Comparision Area | Classic Experience | New Experience |
|------------------|--------------------|----------------|
| Design approach | Topic and flow-based design | Agent-first design |
| Authoring style | Explicit conversation nodes and branching logic | Natural-language-driven instructions and behavior |
| Main control mechanism | Topics, trigger phrases, nodes, and actions | Purpose, instructions, knowledge, tools, skills, model, and behavior |
| Navigation | Topics, Knowledge, Actions, Settings | Build, Preview, Evaluate, Monitor |
| Orchestration | Explicit conversation flow design | Enhanced orchestration for reasoning and response quality |
| Best suited for | Scenarios requiring detailed control over conversation flow | Scenarios requiring flexible, intelligent agent behavior and reasoning |
| Maker experinece | More explicit and structured | More natural and intuitive, focusing on agent behavior and reasoning |
| Testing approach | Separate testing and evaluation | Preview and Evaluate tabs |
| Monitoring | Available but less control to authoring | Monitor tab integrated with authoring and part of core lifecycle |
| Migration | Existing classic agents remain in classic experience | New agents are created in the new experience, with migration options available |

## What the New Experience Does Better
The new experience improves the maker journey in several ways.
- It simplifies agent creation. Makers can describe the agent’s purpose in natural language rather than starting with detailed topic structures.
- It provides a more unified design surface. Instead of jumping between separate sections, makers can configure identity, instructions, knowledge, tools, skills, and model from the Build experience.
- It makes evaluation and monitoring more visible. Microsoft’s new authoring surface includes Build, Preview, Evaluate, and Monitor as core tabs, which helps makers treat quality assurance as part of the agent lifecycle rather than an afterthought.
- The enhanced orchestration model is designed to improve reasoning and response quality, especially when working with Microsoft 365 data.

## What the Classic Experience Still Does Better
The classic experience is still important.

It gives makers stronger deterministic control over conversation flows. If you need to define every question, every condition, every branch, and every possible path, the classic experience may still be the better choice.

For example, classic experience is useful for:
| Scenario | Why Classic may fit better |
|---------|---------------------------|
| Structured intake forms | When you need to guide users through a strict sequence of questions and actions, classic topic-based design allows for precise control. |
| Compliance-driven interactions | In scenarios where regulatory compliance requires explicit conversation paths and logging, the classic experience provides a clear structure. |
| Complex topic logic | If the conversation requires intricate branching and conditional logic, the classic experience allows for detailed configuration. |

## When Should You Use the New Experience?
Use the new experience when:

| Use case | Why New may fit better |
|----------|----------------------|
| You are creating a new agent | The new experience is designed for modern AI agent design, making it easier to start from scratch with natural-language-driven instructions. |
| You want simpler authoring | The new experience reduces the need for detailed topic and node configuration, allowing makers to focus on the agent's purpose and behavior. |
| You need better reasonign | The enhanced orchestration model in the new experience improves reasoning and response quality, especially when working with Microsoft 365 data. |
| You use M365 data | The new experience is optimized for agents that leverage Microsoft 365 data, providing better integration and reasoning capabilities. |
| You want lifecycle based design | The new experience integrates Build, Preview, Evaluate, and Monitor into the authoring surface, encouraging makers to consider the full lifecycle of the agent. |

## When Should You Use the Classic Experience?
Use the classic experience when:

| Use case | Why Classic may fit better |
|----------|----------------------|
| You arelady have a classic agent | If you have an existing agent built in the classic experience, it may be more efficient to continue using that interface for maintenance and updates. |
| You need deterministic control | If your agent requires precise control over conversation flows, branching logic, and explicit paths, the classic experience provides the necessary tools. |
| You rely on classic features | If your agent depends on specific features or configurations available only in the classic experience, it may be best to stick with that interface. |
| You want precise branching logic | If your agent's functionality relies heavily on complex branching and conditional logic, the classic experience allows for detailed configuration. |

## Important Limitation: No Direct Migration (Till Now)
One of the most important points is that there is no direct conversion path between the two experiences.

Agents created in the new experience cannot be transferred to the classic experience. Similarly, agents created in the classic experience cannot be transferred to the new experience. Microsoft explains that this is because the two experiences use fundamentally different architectures and orchestration runtimes.

This means makers and architects should decide carefully before starting a new agent. For enterprise teams, this decision should be part of the solution design stage.

## Enterprise Architect View
From an enterprise architecture perspective, the decision should not be based only on which interface looks newer.

The better question is:
<pre>
"What level of control, governance, reasoning, extensibility, and maintainability does this use case need?"
</pre>

**Decision View (This is my personal view, not Microsoft’s official guidance):**

| Question | Preferred Experience | Why |
|---------|--------------------|-----|
| Do you need step-by-step control? | Classic | If your use case requires precise control over every step in the conversation, the classic experience provides the necessary tools. |
| Are you building a new agent from scratch? | New | The new experience is designed for modern AI agent design, making it easier to start from scratch with natural-language-driven instructions. |
| Does the agent need to reason over Microsoft 365 data? | New | The enhanced orchestration model in the new experience improves reasoning and response quality, especially when working with Microsoft 365 data. |
| Do you need exact topic-level branching? | Classic | If your agent's functionality relies heavily on complex branching and conditional logic, the classic experience allows for detailed configuration. |
| Do you want a lifecycle-based design approach? | New | The new experience integrates Build, Preview, Evaluate, and Monitor into the authoring surface, encouraging makers to consider the full lifecycle of the agent. |

The new experience is the direction of travel for AI agent design, but the classic experience remains relevant for structured, deterministic, and existing bot scenarios.

## Closing Thought
The shift from classic to new Copilot Studio experience reflects the larger shift happening in enterprise AI.

**Simple Summary**
<pre>
<b>Classic Experience</b> = Topic-first, node-based, deterministic, explicit control
<b>New Experience</b> = Agent-first, instruction-based, reasoning-driven, lifecycle-oriented
</pre>

We are moving from:
<pre>
Chatbot design → Agent design
Topics → Instructions
Triggers → Reasoning
Flows → Tools and skills
Manual testing → Evaluation and monitoring
Single bot → Connected agent ecosystem
</pre>

For makers, this means faster and more intuitive authoring.

For architects, it means stronger governance around instructions, knowledge, tools, model selection, environment strategy, DLP, security, and lifecycle management.

The new experience is the future-facing direction, but classic experience still has a place where precision and deterministic control matter.
