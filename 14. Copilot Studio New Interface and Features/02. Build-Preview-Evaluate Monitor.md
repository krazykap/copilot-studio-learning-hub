# Build, Preview, Evaluate, Monitor in the New Copilot Studio Experience
The new Microsoft Copilot Studio experience introduces a cleaner and more lifecycle-driven way to build agents. Instead of treating agent creation as only a design-time activity, the new interface organizes the maker journey around four major tabs:

`Build → Preview → Evaluate → Monitor`

This structure is important because a good enterprise agent is not complete when it is created. It must be configured, tested, evaluated, published, monitored, and continuously improved.

Microsoft describes the new agent experience as a redesigned authoring and runtime environment with a natural-language-first approach, a unified single-surface design, and enhanced orchestration for improved reasoning and response quality. The new authoring surface is organized around **Build, Preview, Evaluate,** and **Monitor** tabs.

In the classic Copilot Studio experience, makers often focused heavily on topics, triggers, nodes, conditions, and conversation flows. That approach worked well for structured chatbots, but modern AI agents need a broader lifecycle.

An agent needs to answer questions, use knowledge, call tools, perform actions, handle ambiguity, respect instructions, and improve over time. The new interface supports this by placing the agent lifecycle directly into the maker experience.

The four tabs help makers think in this sequence:

| Stage | Main Question |
|-------|----------------|
| Build | How do I create an agent that can answer questions, use knowledge, call tools, perform actions, handle ambiguity, respect instructions, and improve over time? |
| Preview | How do I test the agent to ensure it behaves as expected in real-world scenarios? |
| Evaluate | How do I assess the agent's performance, identify areas for improvement, and ensure it meets quality standards? |
| Monitor | How do I track the agent's performance over time, gather feedback, and make continuous improvements? |

This is a major improvement because testing, quality assurance, and monitoring are no longer separate afterthoughts. They become part of the normal agent development loop.

## 01. Build: Configure the Agent Foundation
The Build tab is the main design surface in the new Copilot Studio experience.

This is where you configure:

| Build Area | Purpose |
|------------|---------|
| Agent Identity | Defines what the agent is and what role it plays |
| Instructions | Defines behavior, tone, scope, boundaries, and escalation |
| Knowledge Sources | Connects the agent to approved information sources |
| Tools | Allows the agent to take actions or call systems |
| Skills | Adds reusable capabilities to the agent |
| Model | Defines the underlying AI model and its parameters |

Microsoft’s new experience uses a tab-based surface where the Build tab is used to configure the agent’s identity, knowledge, tools, skills, and model. The new experience also moves away from explicit topic-first design and toward natural-language instructions and reasoning-driven behavior.

#### Build Tab Example
The Build tab is where the agent’s foundation is created. A weak foundation leads to weak responses, even if the interface is modern.

For an HR policy assistant, the Build tab might include:

| Area | Example Configuration |
|------|---------------------|
| Agent Identity | "HR Policy Assistant" |
| Instructions | "You are an HR policy assistant. Answer questions about company policies, provide guidance on procedures, and escalate complex issues to HR staff." |
| Knowledge Sources | Company HR policy documents, internal knowledge base, FAQs |
| Tools | HR ticketing system, calendar scheduling tool |
| Skills | Document summarization, policy search, escalation workflow |
| Model | GPT-4 with specific fine-tuning for HR context |

#### What Makers Should Focus on in Build?
When working in the Build tab, makers should not only add knowledge and tools. They should define the agent carefully.

A good Build configuration should answer:

<pre>
Who is the agent?
What is the agent allowed to answer?
What sources should the agent use?
What actions can the agent perform?
When should the agent ask a clarification question?
When should the agent refuse or escalate?
What tone and format should the agent use?
</pre>

This is especially important in enterprise scenarios because agent behavior must align with security, compliance, operational process, and user expectations.

## 02. Preview: Test the Agent Interactively
The Preview tab allows makers to test the agent before publishing it.

This is where you interact with the agent like an end user. You can ask questions, validate responses, test knowledge grounding, check how instructions are followed, and confirm whether the agent invokes the correct tools.

Microsoft describes the Preview tab as the place to test the agent interactively in a preview chat interface. The broader lifecycle guidance also positions Preview and Evaluate as the testing stages before publishing.

#### What to Test in Preview?
Preview testing should not be random. Makers should test both expected and unexpected scenarios.

| Test Type | Example |
|-----------|---------|
| Happy Path | "What is the company's vacation policy?" |
| Ambiguity Handling | "Can you tell me about the policy?" (without specifying which policy) |
| Out-of-scope Questions | "What is the weather today?" |
| Knowledge Grounding | "According to the HR policy document, what is the procedure for requesting leave?" |
| Tool invocation | "Schedule a meeting with HR for next Monday." |
| Escalation | "I have a complex issue regarding my benefits. Can you help?" |
| Tone and Format | "Please provide a concise summary of the policy in bullet points." |

The Preview tab is best for interactive exploration. It helps makers understand how the agent behaves in a realistic conversation.

#### Preview Is Not Enough
**Preview** is useful, but it is not a complete quality assurance strategy.

The limitation is that preview testing is usually manual and conversation-by-conversation. It helps you explore behavior, but it does not easily prove that the agent is consistently working across many scenarios.

That is why the next stage, **Evaluate**, is important.

## 03. Evaluate: Measure Agent Quality with Test Sets
The **Evaluate** tab is where Copilot Studio becomes more serious about quality measurement.

Instead of testing one question at a time, makers can create and run test sets. A test set allows multiple test cases to be executed together so that the agent can be assessed more consistently.

Microsoft explains that agent evaluation can generate, import, or manually create test cases as a test set. Test sets allow makers to run multiple test cases at once, analyze aggregate scores, and zoom in on individual test cases. When an evaluation runs, Copilot Studio sends questions to the agent, records responses, compares them against expected responses or quality standards, and assigns scores.

### Preview Vs Evaluate

| Area | Preview | Evaluate |
|------|---------|----------|
| Purpose | Test the agent interactively | Measure agent quality with test sets |
| Testing style | Manual, one conversation at a time | Automated, multiple test cases at once |
| Best for | Exploring behavior, understanding responses | Assessing performance, identifying areas for improvement |
| Scope | Individual questions and responses | Aggregate scores, overall quality assessment |
| Output | Immediate feedback on specific interactions | Comprehensive evaluation report with scores and insights |

It's important to note that **Evaluate** is not just about testing. It is about measuring quality, identifying weaknesses, and ensuring that the agent meets the desired standards before it is published.

### Evaluation Methods
Copilot Studio supports different evaluation methods depending on what you want to measure.

| Evaluation Method | What it Measures |
|-------------------|------------------|
| General Quality | Overall performance of the agent across various scenarios |
| Compare meaning | How well the agent's responses align with expected answers or quality standards |
| Tool use | Whether the agent correctly invokes tools when needed |
| Keyboard matching | How well the agent's responses match expected text or patterns |
| Text similarity | How similar the agent's responses are to expected answers in terms of meaning and context |
| Exact Match | Whether the agent's responses exactly match the expected answers |
| Custom | | Allows makers to define their own evaluation criteria based on specific needs |

**[Evaluation guidance](https://learn.microsoft.com/en-us/microsoft-copilot-studio/analytics-agent-evaluation-overview)** explains that different methods are available for different evaluation needs, including general quality, compare meaning, and tool use.

## 04. Monitor: Understand What Happens After Publishing
The **Monitor** tab helps makers understand what the agent is doing after it is published.

This is where the agent lifecycle moves from design-time testing to real-world operational visibility.

Microsoft states that the Monitor tab gives visibility into agent performance and activity after deployment. It can be used to track conversation sessions, review analytics, identify errors, and understand how users interact with the agent. The Monitor tab becomes available after the agent is published.

### What You Can Monitor?
The Monitor tab can show information such as:

| Monitoring area | Why it matters |
|-----------------|----------------|
| Recent tasks | Understand what the agent completed or attempted |
| Task status | Identify successful, failed, or in-progress activity |
| Files accessed | See which files the agent used during interactions |
| Activity context | Understand the context of conversations and actions |
| Analytics | Review metrics such as response times, user satisfaction, and usage patterns |
| Errors | | Identify issues that need attention or improvement |

**[Monitor documentation](https://learn.microsoft.com/en-us/microsoft-copilot-studio/agents-experience/authoring-review-activity)** explains that the Monitor tab shows recent tasks, task status, timestamps, task context, and files the agent accessed or used. It is especially useful for agents that take autonomous actions, such as sending emails, updating records, or interacting with Microsoft 365 services.

## The Full Improvement Loop
The real value of the new interface is not in the individual tabs. It is in the loop they create.
<pre>
Build the agent
↓
Preview the behavior
↓
Evaluate against test cases
↓
Publish when ready
↓
Monitor real usage
↓
Improve instructions, knowledge, tools, and tests
↓
Repeat
</pre>

This is the operating model enterprise teams should adopt.

A mature Copilot Studio team should not only ask:
<pre>
“Did we build the agent?”
</pre>

They should ask:
<pre>
“Did we test it, evaluate it, monitor it, and improve it based on evidence?”
</pre>

## Enterprise View
From an enterprise architecture perspective, the new Copilot Studio interface encourages a more disciplined delivery model.

| Lifecycle Area | Focus |
|----------------|-------|
| Build | Design guardrails, approved knowledge, tool boundaries, model selection |
| Preview | Validate behavior against real user journeys |
| Evaluate | Define measurable quality criteria and regression tests |
| Monitor | Review operational performance and adoption |
| Improve | Feed monitoring insights back into design and governance |

This is especially important for agents that access enterprise data or perform actions. The more capable the agent becomes, the more important the lifecycle becomes.

## Closing Thoughts
The new Copilot Studio interface makes one thing clear:

`An agent is never “done” after the first build.`

A well-designed agent must be built carefully, previewed with realistic scenarios, evaluated with repeatable test cases, monitored after publishing, and improved continuously.

That is the real value of the new experience.

It moves Copilot Studio from a chatbot builder mindset to an enterprise agent lifecycle platform.
